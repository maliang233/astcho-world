# 正式启动与 QQ 私聊分流

2026-10-28 按用户要求启用。管理员取本地 `.env` 的 `ASTCHO_ADMINS`，保持与原项目相同的逗号分隔 QQ 号配置。昵称、消息自称、引用和群管理员头衔不能授予权限。

## 启动

双击 `启动星回.command` 启动 `serve --qq-transport reverse_ws --runner dsh`。已在正式运行则只打开 Web；发现本启动器管理的旧观察服务则先关闭，再运行主体。缺少模型或管理员配置时明确报错，不再降级到观察模式。

本地 `config/apps.local.json` 的 QQ `conversation.allow_send` 已按此次授权设为 true。群聊沿用原概率通知和显式观察；用户随后授权将默认回复改为主体组织正文并调用 `reply_group`，原聊天服务继续处理状态和发送，详见 [群聊主体回复](QQ_SUBJECT_REPLY.md)。网页管理查询不改变星回的观察。

## 管理员私聊

每条真实管理员私聊单独保存为 `admin_requests`，不经过群聊概率或 2–5 秒聚合。传输层核验身份后唤醒同一个 World/DSH 主体，使用持久会话与现有工具。多个请求串行处理；不会为管理员另建一套竞争的决策循环。

实际输入的 `world.wake.admin_request` 包含请求 ID、发送者 QQ 号、原文、`chat_id/message_id` 和 `authority=configured_admin`。只有运行时附加的此字段表示管理员请求。请求正式交给主体时才记录观察，未取出的排队正文不会通过普通通知或摘要进入模型。

任务结果或澄清通过显式 `qq.reply_admin` 工具发回私聊，不自动把普通环境输出发送 QQ。工具再次检查收件人属于配置管理员、目标是私聊、锚点确实为该用户发来的消息，并按操作 ID 保留投递状态。文本以 OneBot text segment 发送，不把正文中的 CQ 字符串解析为其他动作。非管理员和群聊无法成为该工具的收件人。

同一入站消息重投不会新建任务。重启时恢复待处理项；执行中的请求标记为 interrupted，不盲目重放可能已写入或已发送的操作。processed 仅代表本轮处理结束，具体完成、暂停或失败以活动与工具回执为准。管理员权限撤销后，尚未执行的请求标为 revoked。

## 非管理员私聊

消息保存在 QQ App 中，直接走原私聊 Replyer，不进入 World 通知或管理员请求队列。原 handler 的空文本、`/`/`.` 开头过滤、每用户锁、50 条 deque、latest 先进入历史、管理员表达反馈检查和原 `private_reply` 调用契约保持一致；原 prompt、模型参数与清洗不变。没有向这个模型提供 World/DSH 工具。

QQ App 内部创建稳定的私聊快照，用原参与接口记动作回执。World 记录回复动作及消息 ID，不自动收到普通私聊原文。发送回显不被当作新用户请求。普通用户自称管理员仍只走聊天路径。

## 本机 NapCat

本机 Docker 容器 `napcat` 的既有反向客户端从 8080 改为 `ws://host.docker.internal:8091/onebot/v11/ws`。既有鉴权令牌迁入本地 `ASTCHO_WORLD_WS_TOKEN`，没有关闭鉴权。NapCat 保留同一 QQ 数据卷，并设置既有星回账号快速登录，以便恢复重启后的会话。

修改前的 `.env`、App 配置和 NapCat 配置保存在 Git 忽略的 `var/backups/`，权限为 0600。文档不记录密钥或真实私聊正文。此次没有手工向 QQ 发送测试消息；正式启用后，真实入站消息会按上述规则处理。
