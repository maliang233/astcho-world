# 视频详情与压缩修复（2026-10-29）

## 原因

旧 `video` 将 B站 `get_info()` 整份结果直接交给主体。平台可能在 `ugc_season` 中附带整个合集，每一集还嵌套完整资料；此次单份工具消息约64.7万字符，其中合集约62.5万字符。它属于当前活动工具链，不会随近期活动简述缩短而消失。

原生DSH保留近期尾部并保证工具调用/结果配对。一个巨大的近期工具结果会使前面只剩旧压缩检查点可选；重写它不一定更小。此外，通用压缩检查还会在World确认真正的模型步骤之前执行，包括维护与普通完成后的结束探测。压缩时携带主体system、工具schema又增加了无关输入与误选工具的风险。

## Bilibili App 0.1.2

- `video` 仅返回本视频所需资料、分页分P目录、合集名称与条目数量，不自动展开整个合集。`page`/`limit` 分页，默认10条；`source_ref` 指向本次取得的完整原始资料。
- 新增 `collection(bvid, source_ref?, page?, limit?)`，按需读取合集候选目录。每集只提供定位、标题、时长等，不嵌套其他视频的完整资料。
- 分P和合集可沿用同一个 `source_ref` 读取，避免重新请求平台。App私有目录保存完整资料，SHA-256校验、视频身份核验与严格引用格式防止读错或任意文件访问。
- 本地 `history` 返回浏览记录索引，避免再次附上三十份字幕、图片观察或旧的大详情。原始浏览记录仍保存在App数据库；原实际工具结果可经World经历回看。

## 当前会话及压缩

- 旧B站详情通过官方SDK的持久 `surfaceOp` 替换工具结果的内容。工具调用ID、消息ID、回执与结果状态不变；原日志及World完整结果保留，投影带原事件编号和App分页引用。不会重放工具或伪造新回执。
- 相同投影还供活动摘要使用，避免归档整理重新读入旧合集全文。World只按操作编号替换摘要输入中的结果数据，原事件、归档文件及操作状态不改；其他App没有登记投影时仍按原始已观察记录整理。
- 已送达通知的历史编号列表是重复状态，不是新消息。DSH唤醒只附历史数量；旧唤醒的编号列表也改为数量，原时间、原因、新通知与管理员消息保留，原记录仍在。
- World先完成维护/结束探测的识别，仅在确实需要下一步模型决策时调用同一个原生DSH压力压缩引擎；原生溢出恢复仍保留。不在初始化、活动归档或本地检查上顺带发起付费压缩。
- 若原生选择只剩一条旧检查点，压力压缩可扩到下一段完整且配对平衡的实际内容。仍由原生事务验证边界、缩短幅度与重放；若没有新经历，不付费重写相同检查点。
- 压缩调用使用独立的只读system和作为资料的原始记录，不带主体人格、行动工具schema或可执行工具。保留事实引用和精确操作状态；完整来源关系由SDK事务记录，不重复塞入每个摘要。

没有增加总输入token上限、强行截断、生活安排或第二个行动主体。原聊天、视觉prompt及人格原文保持字节不变。

## 验证边界

自动测试使用真实SDK和本机合成模型，覆盖超大合集、分页完整性、同份资料离线读取、非法引用、浏览历史不重放大正文；旧工具结果投影、来源回看、操作身份、跨重启和调用配对；有压力时维护不触发模型；旧检查点与巨大工具结果可以一起进行合法压缩。

恢复前备份World、Bilibili数据库、SDK日志与经历归档。在真实私有副本上先用断网模型配置进行纯本地投影及重放检查，再用本地模型替身验证一次普通续跑；真实恢复仅进行一次只读压缩，不运行App或发送测试消息。

完整工作区回归377项通过，唯一失败仍是受保护原版prompt的既有断言。最后一次步骤准入顺序调整后，相关32项真实SDK/合成模型测试全部通过；Ruff与本地原项目字节基线核对通过。

副本的本地续跑只产生1次合成模型请求，输入约54,837字符，未重放App操作。副本与正式会话分别进行了1次实际只读压缩，每次仅1个模型请求、0个App步骤。期间服务曾重新运行而形成新分支，因此没有用旧副本覆盖正式数据，而是备份最新记录后在当前同一Session内应用SDK投影与压缩。正式当前表面从投影后的71,602降到11,005字符，保留完整原始日志，操作及通知台账核对不变，关闭后再次重放通过。

正式服务已加载Bilibili 0.1.2，NapCat反向WS连接正常，无活动归档错误。以上字符计数不是提供商token计数；实际正常运行用量以提供商回执为准。

初次恢复后的正常活动已经完成“读取QQ → 选择不回复 → 结束”，首个正常请求提供商报告11,909未缓存输入加3,072缓存输入，即14,981输入token。随后活动归档暴露了另一条旧数据入口：原始合集从观察档案再次进入活动摘要，产生一次274,457输入token的失败请求。这是额外的实际消耗，不能计为已避免；已停下并补齐摘要输入投影。

补齐后，待整理源从约78.5万降到13.5万字符，完整原文保持不变；只用1次实际只读摘要调用整理该已结束活动，既有合格摘要复用，没有重整所有历史。随后经原生SDK归档投影移除该已结束活动的完整可见历史，最近简述常驻820字符，归档错误清除，关闭后再次重放通过。
