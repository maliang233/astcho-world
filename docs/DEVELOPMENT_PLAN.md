## 1. 先理解用户要什么

目标是给星回打造一个可以自主感知、选择和行动的环境。

用户不希望继续细化一套“星回应当如何生活”的程序。开发者提供应用、能力、信息入口和运行条件，星回自己决定关注什么、使用什么，以及是否行动。

QQ 从唯一的世界变成环境中的一个 App。以后能够继续加入新的 App、插件和 Skill；应用有统一设计规范，相互独立，不因一个应用的故障或变更破坏其他应用。

用户已经提出的 QQ 体验：

- 原来触发 Planner 的机会改为通知机会，概率尽量沿用原设计。
- 通知只展示来源和触发的单条消息，不自动附上群聊上下文。
- 星回可以忽略，也可以选择打开群聊、读取上下文，再继续决定。
- 群聊可以设置免打扰；普通群消息不通知，明确 @ 星回或回复星回时例外。
- 免打扰不影响消息保存和主动访问。即使没有通知，星回也可以打开 QQ 查看记录。
- 不应仅根据人数自动替星回决定哪些群免打扰。提供设置能力，具体策略由用户配置或星回选择。

“提供自主选择”与“保留聊天表现”必须同时成立。不要用新架构重写一个聊天风格不同的星回。

## 2. 不可越过的兼容性边界

### 2.1 原代码是依据

基准是本地 GitHub 版，包含未提交改动。不能只看 Git HEAD，也不能用线上版本覆盖本地。另一旧项目目录不是此次基准。

用户明确要求后续执行者亲自阅读代码，避免转述造成信息失真。因此本计划不描述原实现的具体参数、函数行为或算法细节。实施前自行查证，不把前序聊天中的代码解释当作规范。

### 2.2 原有 prompt 一个字都不能改

用户没有明确要求时，所有原有 prompt 保持原样。这包括嵌入在业务代码中的提示、模板、拼接文本及相关构建逻辑，而不只是某个 prompt 文件。

不得借“适配 agent”“统一人格”“减少 token”“增强自主性”修改原 prompt。不得在原调用外偷偷追加新的指令来改变其行为。

新增环境决策提示可以单独设计，但必须与原聊天提示分离；只说明可用能力、事件和操作规则，不重新定义星回的聊天人格，不规定生活目标。

### 2.3 聊天行为尽量原样保留

优先复用原代码与既有测试。保持原模型调用方式、上下文组织、决策与回复分工、输出处理、会话隔离等已验证设计，具体内容以实操时读到的代码为准。

迁移原则：改变进入聊天能力的入口，不默认改变能力本身。

星回选择进入聊天后，调用原有聊天能力。外层环境 agent 不应再次润色、重写或替换其输出。不能为了让外层“一把完成”而合并、删除原有聊天阶段。

若原实现存在后台学习、自动发送或其他不经过新选择入口的行为，必须列为兼容性冲突项。不能既保留未读信息泄漏或自动发送旁路，又声称已完成自主环境；也不能擅自删除原行为。先提出最小适配方案，必要时向用户确认该行为边界。

### 2.4 允许发生的差异要明确

明确授权的新变化是：通知与上下文分离、可忽略通知、免打扰、主动访问应用、支持其他应用。

由于星回可以选择不进入聊天，实际参与次数不可能要求与旧系统完全相同。兼容性比较应在相同输入、状态、时间和随机条件下比较原聊天能力，不能以端到端发言次数不同为借口修改概率或 prompt。

## 3. 目标结构及技术选择原则

建议保留三个清楚的边界：

1. **环境内核**：应用注册、工具路由、通知、时间与后台任务、操作与观察记录。
2. **Agent 运行器**：模型调用和连续决策循环，通过适配器访问环境。
3. **星回能力**：原聊天、人格、记忆等现有能力，保留自身契约，不被运行器重写。

QQ、笔记等 App 接入环境内核；Skill 是可按需读取的使用知识；Plugin 是安装和扩展的技术载体。三者不是同义词。

技术实现原则：

- 先选择最有利于复用原项目的实现方式，不先决定全面换语言或框架。
- 应用契约不依赖某一个模型供应商、QQ SDK 或 harness 的内部类。
- 新增应用通过注册与协议接入，不要求在内核里增加一串应用专属分支。
- 不为追求抽象设计插件商城、复杂分布式系统或完整桌面界面。
- 首版需要真实验证应用故障隔离。独立进程是优先评估方案；仅分模块不等于隔离。

DeepSeek Harness 作为候选，需要核对实施时的官方文档、版本和实际能力。用最小验证判断是否适合，不把前序聊天中的框架描述当作已完成的可行性验证。

候选验证至少覆盖：自定义工具、外部事件、连续工具循环、结束与恢复、上下文可控、调用日志，以及对原聊天模块的无侵入调用。不能自动向原聊天调用注入框架提示。无法满足时保留环境协议，改用简单的自有运行器，不牵连应用重写。

参考入口：

- https://github.com/deepseek-ai/deepseek-harness
- https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md

## 4. 统一 App 规范需要覆盖的内容

第一版先写协议文档和可执行校验，再实现参考 App。

| 项目 | 最低要求 |
| --- | --- |
| 身份与版本 | 唯一 app_id、应用版本、协议版本、简介 |
| 能力发现 | 应用列表、能力说明、按需获取工具定义 |
| 工具接口 | 输入与输出 schema、明确目标、是否有副作用 |
| 结果 | 成功、失败、进行中、取消、结果未知；包含可追踪的操作 ID |
| 事件 | 来源、事件 ID、事件类型、时间、数据引用；支持去重 |
| 通知 | 展示内容与内部定位信息分开；通知不等于任务指令 |
| 数据 | 应用拥有自己的记录、设置、连接和存储命名空间 |
| 生命周期 | 安装、启动、健康状态、停止、升级兼容、卸载后的数据处理 |
| 运行隔离 | 单应用超时、并发、队列和故障不能拖垮全局 |
| 后台任务 | 启动后可查询，完成可产生事件，支持必要的取消与恢复 |
| 使用知识 | Skill 可单独发现、读取和版本化，不自动获得额外权限 |

不要求所有应用都实现同名的 open/read/write。统一接入规范，同时保留 QQ 发消息、笔记保存、浏览器导航等具体语义。

应用不能直接读取其他应用的私有数据库或调用内部对象。跨应用行动由星回通过公开能力组合完成。

事件重投与动作重试必须区分。读取通常可重试；发送消息等操作遇到超时，不能假设未成功后直接重复执行。对不支持服务端幂等的平台，保留“结果未知”并提供查询或人工处置路径，不宣称可以保证严格恰好一次。

## 5. 信息、状态和时间的边界

必须分别记录：

- **应用事实**：应用实际收到或保存的数据。
- **通知状态**：待送达、已送达、忽略等；不得与聊天已读混为一谈。
- **实际观察**：星回通过通知或工具结果实际看到了什么。
- **个人记忆**：基于已发生的经历形成的记忆。
- **动作结果**：决定做、已经尝试、已经成功是不同状态。

应用记录不自动进入模型上下文。未读消息不能通过摘要、记忆检索、表达学习或其他后台通道进入星回的认知。需要迁移旧后台能力时，保留算法与 prompt，单独处理触发和数据来源的边界。

QQ 需要可分页、可定位的记录，而不只是当前模型上下文。只承诺可获得的历史范围；不能假设 QQ 接口能取回任意旧消息。历史缺失要明确返回，不能编造。

一次通知必须稳定引用原始触发消息，不能在执行延迟后用“当前最新消息”替换。读取上下文后，记录本次实际返回的数据范围；后续新消息不会自动补进已经构建的聊天输入。

不要把所有应用记录塞进一个无限增长的对话。维护可恢复的主体活动状态，同时保留原有聊天会话的数据隔离。

模型在未运行时不会自动产生决定，因此要提供时间唤醒和自设提醒能力。提醒用于重新提供选择机会，不自动赋予聊天或发言任务。是否启用低频空闲唤醒及其预算做成配置，不编写生活作息脚本。

首版宜避免多个独立循环同时控制同一个星回的对外行为。通知排队与后台工具任务可以并发，但状态更新和行动归属要明确，不能每来一条消息就新建一个互不知情的主体。

## 6. 分阶段开发

各阶段完成条件是实际可检查的结果，不以“代码已写完”代替验证。无需每阶段都重新请求继续开发；仅在保护边界冲突、必要信息缺失或真实部署前提出具体问题。

### P0：执行者直接调查原项目，建立兼容基线

任务：

- 阅读原项目约定、当前本地代码、配置结构和相关测试。
- 记录工作区状态；识别已提交与未提交内容，禁止覆盖。
- 自行建立聊天入口、prompt、调用参数、状态与副作用的对应清单，引用原文件位置。
- 盘点哪些能力可以原样复用，哪些需要适配，哪些与新环境存在冲突。
- 在隔离环境中运行合适的既有测试；记录已有失败，不能先修改旧实现来获得绿色结果。
- 选择基线保护办法：原 prompt 精确内容校验、固定输入下完整模型请求快照，以及关键行为回放。私密配置与聊天数据不得进入公开夹具。

产物：`docs/COMPATIBILITY.md`、基线测试、变更边界清单。

通过条件：执行者能依据代码说明复用边界；原有 prompt 的任何变化都能被检测；没有把 HEAD 或远端当作本地完整基线。

如果原项目在实施期间发生用户修改，重新核对来源并记录，不能静默刷新基线或覆盖用户变化。

### P1：App 协议和环境内核的最小闭环

任务：

- 写 `docs/APP_SPEC.md`，定义第 4 节中的最小契约。
- 实现注册、发现、调用、事件与通知、状态记录、故障隔离。
- 实现一个 Notes App 作为参考，再用独立的故障测试 App 验证隔离。
- 使用脚本或伪模型执行工具序列；此时不依赖真实模型、不连接真实 QQ。

通过条件：无需修改核心循环即可注册 Notes；同一规范可以校验其他应用；一个应用卡住或退出不阻塞其他应用；停止后仍能正确恢复已完成操作的记录。

### P2：选择并验证 Agent 运行器

任务：

- 对 DeepSeek Harness 做有边界的接入验证，核对它会如何组织模型输入和工具结果。
- 与最小自有运行器比较复用成本、状态控制、部署复杂度和兼容风险，写清选择依据。
- 通过适配器接入 P1 的应用协议。
- 加入独立的环境提示和按需工具/Skill 发现能力。
- 支持继续操作、忽略通知、结束当前活动、自设提醒及恢复。

通过条件：模型能使用 Notes，能选择不行动；运行器不会将普通输出自动当成 QQ 发言；应用实现不导入所选 harness 的内部对象；新环境提示未污染原聊天调用。

### P3：QQ App 的数据与通知能力

任务：

- 从原项目复用可用的 QQ 接入能力，新增持久记录、会话查询、消息读取和定位。
- 把原触发机制适配为通知生成机制。先查清原概率与状态更新规则，尽量复用；不要凭印象重写公式、常量、聚合节奏或随机抽样次数。
- 通知只展示来源与单条触发消息。内部保存稳定定位信息。
- 支持免打扰设置、明确 @ 和回复的例外，以及主动打开没有通知的会话。
- 忽略通知不能擅自记成原 Planner 的 no_reply；通知送达也不能记成实际发言。新旧状态如何对应必须写入兼容性清单。
- 处理原规则与通知例外的冲突，只做满足已授权需求所需的最小适配，并为差异单独验收。

通过条件：普通免打扰消息只进入应用记录；@ 或回复仍可通知；上下文必须通过显式读取进入观察记录；同一通知不会因重放重复触发；可以主动读取免打扰群。

此阶段默认使用合成消息、录制协议夹具或只读接入，不开启真实自动发送。

### P4：接回原版聊天能力

任务：

- 星回选择读取 QQ 上下文后，通过适配层进入原聊天能力。
- 复用原 prompt、上下文构建、模型调用、解析和回复表现；不得让外层模型改写聊天结果。
- 明确进入聊天、生成结果、发送、情绪与关系更新、记忆写入等阶段的边界，具体顺序以原代码为依据。
- 对新增的取消、过期、重试路径，保证没有重复发送和重复状态更新；不要把未发送内容记成已经发生的互动。
- 群聊与私聊分别做兼容验证，不能默认拿一套新通用对话逻辑替换两者。
- 需要搬动代码时先复用后适配；代码移动不等于获得修改原行为的授权。

通过条件：对同一组固定输入，受保护的聊天请求、输出处理和确定性行为与基线一致；选择不打开时不启动原聊天；实际发送只来自明确行动；没有旁路自动回复。

原行为与选择边界有冲突的部分单独处理，不能扩大成全面重构。

### P5：扩展与恢复验证

任务：

- 接入另一个 App，优先选择范围小、依赖清楚的搜索或只读资料应用。
- 验证跨应用选择与操作，不为这个应用修改 QQ 或聊天核心。
- 增加一个可选 Skill，验证按需发现与读取。
- 验证提醒、后台任务、应用离线、进程重启和未完成操作的恢复。
- 写开发者接入指南与运行说明。

通过条件：新增应用只需独立实现、注册和配置；QQ 故障时其他应用可用；重启后未读、已观察、未完成任务与已发送结果不会混淆；没有强制生活行为脚本。

### P6：试运行、对照检查与回退

任务：

- 先完成离线回放、伪模型流程和隔离运行，再整理真实接入步骤。
- 明确旧实例如何停止发送、新实例如何获得唯一发送权，以及如何回退。
- 复用真实配置或数据时走明确的配置与备份步骤，不直接共享可变数据库文件。
- 将可审阅结果、兼容性报告、已知差异和启动命令交给用户。
- 真实对外发言和替换原运行实例需要用户明确授权；不能为了演示自行发送。

通过条件：新环境有完整可重复的运行方式；回退不破坏旧项目；用户能查看具体差异后决定是否试用。

## 7. 验收矩阵

| 场景 | 必须成立 |
| --- | --- |
| 原 prompt 保护 | 文字与格式完全不变，提示构建和调用输入未被暗中改写 |
| 原聊天兼容 | 相同条件下请求与确定性处理一致；模型随机输出不要求逐字重复 |
| 普通通知 | 使用原触发机制的可兼容部分，只展示单条消息与来源 |
| 忽略通知 | 不自动读取群上下文，不发送，不假造原 Planner 决策 |
| 免打扰 | 普通消息不通知，但可主动读取；@ 和回复例外生效 |
| 主动浏览 | 无通知时也能列出会话并读取记录 |
| 信息边界 | 未观察内容没有通过记忆、摘要或学习旁路进入认知 |
| 输出边界 | 外层决策输出不自动发 QQ，不改写原聊天文本 |
| 应用独立 | 停止、卸载或故障一个应用不破坏其他应用 |
| 可扩展 | 加入第三个应用不修改 QQ 和核心决策循环 |
| 恢复与重试 | 不重复发送，不把超时当成功或失败，不重复提交状态变化 |
| 自主时间 | 提醒和唤醒只提供选择机会，不自动安排生活任务 |
| 原项目保护 | 原工作区、配置、数据和独立运行能力保持可用 |

测试重点是兼容性、信息边界、状态变化和应用隔离，不为文档或简单声明堆砌测试。使用固定时间、随机输入和假模型验证行为；实际聊天质量另由用户在受控试运行中评估，不能声称单元测试已经证明“表现完全一样”。

## 8. 第一轮范围与非目标

第一轮交付应是能运行的环境最小版本：统一 App 协议、一个运行器、Notes、QQ 数据与通知、受保护的原聊天接入，以及关键兼容性和隔离测试。

后续再完成第三个 App、Skill 扩展和更全面恢复能力。不要在核心闭环成立前追求大量工具或界面。

本次不做：原 prompt 优化、人格重设计、聊天算法改良、模型更换实验、自动生活日程、自动兴趣培养、插件商城、完整 GUI、多个自主主体协同、未经授权的生产迁移。

## 9. 给执行者的开始指令

先读本项目 AGENTS.md，然后直接阅读本地 GitHub 版原项目，完成 P0。不要依据上一位助手对代码的解释实施，不要先改 prompt，也不要先重写聊天。

提交一份基于亲自调查的兼容性清单后，沿最小闭环逐步推进。普通开发选择自行判断；只有触及用户明确保护的边界时，才带着具体原代码位置、冲突和最小方案提问。不要把所有架构问题都交回用户决定。
